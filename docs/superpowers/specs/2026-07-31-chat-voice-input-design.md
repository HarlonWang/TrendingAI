# chat 语音输入方案评估

> 状态：**最小实现已落地**（PR #73）。定位是尝试性功能——先看用户用不用，再决定要不要往下投入。

## 背景与判断

chat 输入栏此前只有文本输入。但有个前提必须摆在前面：**用户今天已经能语音输入**——Gboard、搜狗、小米输入法都在键盘上自带麦克风，识别结果直接进 `OutlinedTextField`，我们零代码就享受了。

所以这个需求的增量价值不是「从没有到有」，而是入口显性化 + 拿到数据回答「用户到底会不会对着 app 说话」。价值成立，但**不足以支撑一次重投入**——这条判断决定了下面所有取舍。

## 方案选型

| | A 系统 Intent | B 录音+服务端转写 | C 应用内 SpeechRecognizer | D 不做 |
|---|---|---|---|---|
| 麦克风权限 | **不需要** | 需要 | 需要 | — |
| 服务端改动 | 无 | 新端点+配额+防刷 | 无 | — |
| 单位成本 | 0 | 按分钟计费 | 0 | 0 |
| 识别质量 | 依设备，中等 | 高 | 依设备，中等 | 依输入法 |
| 视觉一致性 | 系统弹窗 | 全自控 | 全自控 | — |
| 工作量 | 小 | 2–3 天 + 后端 | 1.5 天 | 0 |

**选 A。** 录音在识别应用进程内完成，我们不申请 `RECORD_AUDIO`——这对 F-Droid 渠道尤其值钱（渠道页逐条列权限，一个看 Trending 的工具多要麦克风是明显的信任成本），也没有服务端成本，可以直接对匿名用户开放。

C 直接排除：付出了 B 的权限成本，只拿到 A 的能力上限。B 留作后手，触发条件见下文。

## 实现

改动集中在 `ChatInputBar.kt`，不碰 shared / ViewModel / engine / 服务端。

1. **按钮**：输入框为空且无待发图时，发送键换成麦克风（`canSend` 此时必然为 false，不会藏起可用的发送键）。仅当探测到识别应用时渲染。
2. **探测**：`Intent(ACTION_RECOGNIZE_SPEECH).resolveActivity(pm) != null`，配套 manifest 声明 `<queries>` 的 **`android.speech.action.RECOGNIZE_SPEECH`**（查的是 Activity；`android.speech.RecognitionService` 是给 `SpeechRecognizer` 查 Service 用的，声明错了 `resolveActivity` 恒为 null，按钮在正常设备上也不出现）。
3. **识别语言**：`Locale.getDefault().toLanguageTag()`，跟随系统而**不跟界面语言设置**——界面用英文的人说的未必是英文。别套用 `ChatApi.resolveLang()` 的 zh/en 口径，那是后端只支持两种摘要语言的约束，识别引擎支持的语言远不止两种。
4. **回填**：取 `EXTRA_RESULTS` 首项，追加到输入框尾部（不覆盖），**不自动发送**——识别错了直接发出去比多点一下更伤。
5. **失败/取消**：**什么都不做**。理由见下节。
6. **埋点**：`chat_voice_start`（点击）+ `chat_voice_result`（成功，带 `chars` 分桶）。完成率 = result / start。

## 为什么失败时静默——这是本方案最贵的一课

`ACTION_RECOGNIZE_SPEECH` 的契约里，**用户主动取消**和**识别应用出错**回传的都是 `RESULT_CANCELED`，不带任何原因。

我们曾试图把它们分开：用 `PackageManager.checkPermission` 查识别应用自己的录音权限做事后判据，未授权就弹引导、给「去设置」深链。**结果是连续三轮代码评审、三轮回归**——判据本身有歧义（未授权既可能是「想授权没走完」也可能是「就是不想给」），围绕它长出的节流状态机则先后犯了「退出页面就失效」和「弹窗停不下来」两种相反的错误，后者比它要修的问题更严重。

砍掉的理由不只是「难写对」，而是**收益本来就低**：

- 两种情况需要的反馈恰好相反（取消要静默、失败要提示），而取消是更常见的那个；
- 权限受阻时我们能做的只是引导用户去修**第三方应用**的权限，而**输入法的麦克风键就在同一块屏幕上**——用户有更近的替代路径；
- 完成率低本身就是信号，需要深究时再加归因不迟。

**教训**：给一个尝试性功能做穷尽的错误处理，复杂度会迅速超过功能本身的价值。分不清的事情就别假装能分清。

## 真机验证

- **小米 13 / Android 16**：麦克风渲染正常、识别可用。首次使用要连闯三道关——MIUI 跳转确认（选「本次允许」的话每次都弹）、小米「系统语音引擎」首启协议页、该应用的录音权限。三道关我们都插不上手，这是方案 A 的结构性代价。
  - 补充发现：`com.xiaomi.mibrain.speech` **没有 launcher 入口**，用户在桌面和应用列表里找不到它。调试期复现无权限状态只能靠 `adb shell pm revoke com.xiaomi.mibrain.speech android.permission.RECORD_AUDIO`。
- **Pixel_9_2（GMS）**：识别应用是 `com.google.android.tts`，权限由**系统在进入识别界面时弹运行时申请**，与小米的应用内协议页不同。没有 MIUI 那道跳转确认，首次体验更顺。取消后静默、输入框不受影响、无崩溃。

## 后续：什么情况下才做方案 B

观察两周，命中任一即可立项：

- `chat_voice_start` 的周触发用户数 / chat 周活用户数 ≥ 10%，且**完成率（`result / start`）持续偏低**——说明有人想用但用不成；
- 有明确的识别质量反馈（技术术语、repo 名识别不准）。

方案 B 自己录音 + 服务端转写，绕开第三方识别应用，上面那三道关一道都不用闯，识别质量也更好——但要背 `RECORD_AUDIO` 权限、隐私政策、按分钟计费的成本和配额设计四笔债。**没有数据支撑就别开这个头。**

⚠️ 语音全程不碰服务端，**没有 D1 兜底**（`chat_send` 还能靠 `chat_logs` 对账，见 `docs/analytics-notes.md`），Aptabase 埋点是唯一可见性来源。上线后尽早确认事件真的有量。

## 明确不做

- **语音对话**（实时打断 + TTS 朗读）：产品形态和成本都是另一个量级。
- **iOS**：chat 是 Android-only 模块（`globalChatScreen` 依赖反转，iOS 侧为 null）。
- **失败归因与引导**：见上文。真要做，正确的做法是上方案 B 拿到真实错误码，而不是在客户端猜。
